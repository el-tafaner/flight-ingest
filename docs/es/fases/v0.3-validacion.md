# v0.3: errores con `thiserror` y validación de plausibilidad

- **Fecha:** 2026-11-07
- **Tag:** `v0.3`
- **Qué queda funcionando:** errores con mensajes legibles, un `IngestError` que agrupa los de los tipos del dominio, y una validación que explica **por qué** rechaza cada estado.

## Objetivo

Los tipos del dominio ya no admiten valores imposibles de construir (v0.1 y v0.2), pero hay datos que son válidos como tipo y absurdos como realidad: una altitud de 90 km, una velocidad negativa, un `squawk` con un 8. En este hito los detectamos **sin descartarlos en silencio**.

## Qué construimos

- `thiserror` en `Icao24Error` y `PositionError`: ahora tienen `Display` y `Error`.
- `src/error.rs`: `IngestError`, que agrupa los errores del dominio con `#[from]`.
- `parse_identity`: una función pequeña que usa `?` para convertir errores (adelanto del parser de v0.4).
- `src/validation.rs`: `validate`, `partition`, `ValidationIssue` y `Rejected`.

## Por qué así

- **`validate` devuelve `Vec<ValidationIssue>`, no un `Result`.** Un `Result` se detiene en el primer error; aquí queremos **todos** los motivos de rechazo, para poder estudiarlos después.
- **`partition` conserva los rechazados con su motivo** (`Rejected`). Descartar datos sin dejar rastro hace imposible saber si el problema está en la fuente o en nuestras reglas.
- **`now_unix` es un parámetro, no `SystemTime::now()`.** Así los tests son deterministas. Es una decisión de diseño habitual: lo que depende del reloj se inyecta.
- **Los umbrales son constantes con nombre** (`MAX_ALTITUDE_M`...). Son aproximados y discutibles: están para que se vean y se puedan cambiar.
- **Los campos ausentes no son un problema.** Un `None` es información legítima, no un dato inválido.

## Viniendo de Python

| | Python | Rust |
|---|---|---|
| Definir un error propio | Una clase que hereda de `Exception`, con `__str__` | Un `enum` con `#[derive(Error)]` y un mensaje por variante |
| Propagar un error | Se propaga solo, sin que aparezca en el código | `?` lo propaga de forma explícita |
| Convertir entre errores | `raise X from e` | `#[from]`: `?` convierte con el trait `From` |
| Procesar una lista consumiéndola | Un bucle; la lista original sigue existiendo | `partition` toma el `Vec` **por valor**: cada estado se **mueve** a un lado u otro |

**Propiedad otra vez:** `validate` recibe `&FlightState` (solo mira) y `partition` recibe `Vec<FlightState>` (se lo queda). Tras llamar a `partition`, el vector original ya no se puede usar, y el compilador lo impide.

**`thiserror` frente a hacerlo a mano:** en v0.1 escribimos `Icao24Error` sin `Display`. `thiserror` genera `Display` y `Error` a partir de los atributos `#[error("...")]`. Lo que ahorra es código repetitivo; lo que esconde es el trait `std::error::Error`, que conviene conocer.

## Qué nos falló

Si olvidas `#[from]` en una variante de `IngestError`, `?` deja de funcionar. El mensaje del compilador (en `rustc` 1.75; en versiones más nuevas puede variar un poco):

```text
error[E0277]: `?` couldn't convert the error to `IngestError`
   |
   |         (Some(lat), Some(lon)) => Some(Position::new(lat, lon)?),
   |                                                              ^ the trait `From<PositionError>` is not implemented for `IngestError`
   |
   = note: the question mark operation (`?`) implicitly performs a conversion
           on the error value using the `From` trait
```

Se lee así: `?` convierte el error usando el trait `From`, y a `IngestError` le falta ese `From`.

**`clippy` rechazó tres `if let` anidados** (`clippy::collapsible_if`) con `rustc` 1.99. El código era correcto y los tests pasaban; es una regla de estilo que `-D warnings` convierte en error. La forma preferida encadena el patrón y la condición (*let-chains*, disponibles en la edición 2024):

```rust
if let Some(alt) = state.baro_altitude_m
    && !(MIN_ALTITUDE_M..=MAX_ALTITUDE_M).contains(&alt)
{
    issues.push(ValidationIssue::AltitudeImplausible(alt));
}
```

Se arregló con `cargo clippy --fix`. Lección: el estilo "recomendado" cambia con la versión del compilador, y por eso conviene pasar `clippy` en CI con una versión fija.

## Decisiones pendientes

- Los umbrales de altitud y velocidad son aproximados. Cuando tengamos datos reales de OpenSky, los revisaremos con evidencia.
- `ValidationIssue` solo se puede comparar con `PartialEq` (no `Eq`) porque lleva `f64`. Es un detalle que conviene entender.

## Pruébalo tú

1. Quita `#[from]` de la variante `Position` de `IngestError` y lee el error. Vuélvelo a poner.
2. Añade una regla nueva: una velocidad vertical (`vertical_rate_ms`) superior a 150 m/s en valor absoluto es implausible. Escribe primero el test.
3. Intenta usar el vector después de llamar a `partition` y lee el mensaje de `use of moved value`. ¿Cómo lo evitarías si necesitaras el vector original?
4. Un avión en tierra (`on_ground == true`) con altitud de 10.000 m, ¿debería ser un problema? Decide si lo añades como regla y justifícalo en una línea.
